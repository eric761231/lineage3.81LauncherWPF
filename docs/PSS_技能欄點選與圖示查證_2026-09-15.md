# PSS 技能欄點選與圖示查證（2026-09-15）

## 背景

`docs/PSS_道具頁_黑魔石與魔法卷軸計畫.md` 的「製作魔法卷軸」規劃裡，BUFF 右上自訂格只能放技能，需要「點技能欄選技能」這個輸入流程，比照背包道具點選（`InventoryDebug_FindJustClickedItem`）。這篇記錄這次查址的結果。

## 已確認可用：點技能欄抓 skillId

位址／結構抄自 RUST 參考專案（`C:\python_training\L1J3.8Launcher(RUST)參考\src\aux\spell_book.rs`，2026-05-01 該專案實機驗證過，同一支 `TW13081901.bin`，位址直接沿用）：

```
[0x00C31324]（SPELL_BOOK_PTR）→ spell_book 物件
  +0x2C：技能數量
  +0x58：技能 entry 指標陣列
    entry+0x00：vtable
    entry+0x04：packed_skill_id（= skillId − 1，玩家實際學會的版本）
    entry+0x08：「剛被點擊」瞬間會短暫非 0 的旗標（**本次實機驗證成立**，
                跟背包 BAGITEM_INFO+0x08 同一套手法）
    entry+0x0C：名稱字串指標（Big5，含 " (mp/range)" 字尾）
```

實作：`InventoryDebugHook.cpp` 的 `InventoryDebug_FindJustClickedSkill()`，用法比照 `InventoryDebug_FindJustClickedItem()`，在 `WM_LBUTTONUP` 當下呼叫。已實機測試多組技能（初級治癒術/指定傳送/負重強化/援護盟友/閃亮之盾等），`packed+1` 對照伺服器 `skills` 表的 `skill_id` 全部吻合。

**目前狀態**：只接了診斷 log（`[Pss][diag] found clicked skill ...`），還沒接進 PSS UI 的 picking 流程（`PssOverlay_IsPicking`/`PssConfig_SendResolveItemRequest` 那一套），也還沒做「只在 BUFF 自訂格 picking 時才抓」的節流——現在是每次滑鼠放開都會掃一次整本技能書（約 100 多筆），量不大但沒有必要,之後要轉正式時記得比照道具的作法加上 picking 狀態限制。

## 已確認排不通：技能圖示（icon）

原本猜測 icon 跟 skillId 在同一個地方，結果查了三個方向，全部排除：

1. **spell_book entry 物件本身**：只有前 16 bytes 有資料（vtable/packedId/旗標/名稱指標），後面到 80 bytes 全是 0，沒有藏 icon。
2. **spell_db 記錄**（`[0x009A8ED4]` → `base+packed*4` → record，`+0x00` 起是 Big5 名稱字串）：反組譯 `CSpellListXML::parse`（`0x745670`）確認 XML schema 裡有 `icon` 屬性，setter 在 `0x745220`，寫入的是另一個 56 bytes（0x38）「config 物件」的 `+0x14`，不是 spell_db 這個記錄結構——兩個是不同的資料。掛 hook 在 `0x745220` 進入點（見下）實測發現這個 setter **在正常遊玩流程裡完全沒被呼叫過**，代表 `CSpellListXML::parse` 這條路徑不是正式客戶端在跑的（可能只在建置工具/產生快取時用一次），offline 反組譯抓到的資料流程在 runtime 是死的。
3. **伺服器 `S_SkillList` 封包**（`com.lineage.server.serverpackets.S_SkillList`）：只送 `[學會技能, 等級]` 的 32-byte bitmask，`L1Skills` 樣板也沒有 icon 欄位，確認伺服器端完全不送 icon，純客戶端資料。

**追加驗證（同一天稍晚）**：怕是 setIcon 這個下游 setter 沒被呼叫到、但 `CSpellListXML::parse` 本體其實有跑（例如走到一半提早 return），所以另外直接在 `parse()` 本身的進入點（`0x745670`，機器碼特徵 `55 8B EC 6A FF`）掛了一個更上游的探測 hook。**結果：登入、進世界、開技能欄視窗、點技能，全程都沒有觸發過一次**——不是「setIcon 沒被叫到」，是整個 `CSpellListXML::parse` 函式本身在正式客戶端裡完全沒有被呼叫。徹底排除這整條路徑，不是猜測，是兩層都驗證過。

也試過直接看客戶端安裝目錄有沒有原始 XML 檔可以直接讀（繞開記憶體）：沒有找到任何 `.xml`，只有一堆 `.pak`/`.idx`。`Text.pak`（約 25MB，最像放文字資源的檔案）裡雖然搜得到 `spell` 這個位元組序列，但周圍是看起來加密/壓縮過的亂碼，不是真的 XML 內容，是巧合命中，這條路也死了。

排除完所有已知線索後，剩下的方向是**反組譯「技能欄視窗實際畫圖示」那個原生繪製函式**，直接抓它被呼叫時傳進去的 icon 參數（不管資料實際存在哪個結構、怎麼被組出來，畫的當下一定要有個數字）。這個函式位址還沒找到，靜態反組譯目前没有更多線索可以往下切，2026-09-15 這次改成請使用者用 Cheat Engine 做**純數值掃描**（不下中斷點，這個客戶端會擋中斷點但目前沒觀察到擋一般記憶體讀取）去抓「游標移到不同技能時，哪個位址的數值會跟著變」，抓到候選位址後再回頭反推是哪個結構、offset 多少：

1. CE 附加到 `TW13081901.bin`。
2. 技能欄視窗開著，滑鼠停在技能 A 上，CE 開 4-byte「Unknown initial value」First Scan。
3. 滑鼠移到明顯不同的技能 B，CE 切「Changed value」Next Scan。
4. 再移回 A，「Changed value」Next Scan；再移到 C，「Changed value」Next Scan；重複 3~4 輪縮小候選範圍。
5. 篩出候選位址後人工檢查數值是否像「圖示編號」（小整數），把位址跟對應技能告訴開發者，才能回推結構/offset 寫進 DLL。

### 請貼回來的格式（一次一組）

不要只丟一個位址。每輪縮小後剩下的**每個候選**請帶：

```
技能A名稱 / packed+1（若有 log：[Pss][diag] found clicked skill）
  滑鼠停在 A：位址=0x........  值=........（十進位也寫）
技能B名稱：
  停在 B：同一位址 值=........
模組：TW13081901.bin+偏移（CE 模組欄）
該位址前後 32 bytes hex
這是「只懸停」還是「點下去」才變
```

**不要信** `SPELL_WINDOW_MEMORY_BRIEF.md` 寫的 `entry+0x0C = iconObj`：Rust／本次實機已確認 `+0x0C` 是**名稱 Big5 指標**，entry 前 16 bytes 以外全 0。dump 那欄過期。

較省候選的掃法（可選）：先對 `[0xC31324]` 解出 SpellWindow 物件，只掃**該 heap 物件 ±幾 KB**，或技能欄開著時掃 4-byte。全進程 Unknown 也可以，但會很多雜訊。

已知繪製／點選 VA（找不到數值時再給 hook AI 對呼叫點，**本客戶端會擋 BP**，優先仍用數值掃描）：

| VA | 角色 |
|---|---|
| `0x743D20` | 技能格 hit-test（格 0x22×0x22，一頁 8 ICON） |
| `0x744070` | 點選處理 |
| `[0xC31308]` | 施放中 skillId（點一下還沒放術時通常不是 hover 圖示） |

圖示若是小整數，之後多半走道具同一套 `<gfxid>.tbt`／`Sprite.idx`（見 AutoPotion 圖示交接）。`CSpellListXML::parse`（`0x745670`）已證實 runtime **從不呼叫**，CE 不必再往 XML 找。

**背景動機**（供之後接手的人參考優先順序）：這不只是為了畫圖示好看，使用者提到之後要做「各職業可學新技能、技能欄位可以被擴充」，代表技能書/技能欄這整塊記憶體結構未來會需要更深入、更全面地掌握（不只是讀 icon），這次的 `SPELL_BOOK_PTR`／`entry` 結構、`CSpellListXML` 死路的排除結果，都是這個更大目標的基礎調查，不是只服務單一顆 icon 需求。

## 已知線索（不是這次要用的）

- `SpellWindow` 建構子 `0x73B990`：vtable 寫 `0x8EF26C`，跟 `spell_book` 物件同一個 vtable——證實我們用的 `SPELL_BOOK_PTR` 本體其實就是 `SpellWindow` 的資料模型，不是另一個東西。
- `0x962ED8`／`0x962F58`：兩個 WORD 表，被複製進全域 `0xC31220` 陣列（48+8=56 格），是某種「預設技能清單/快捷列」初始化資料，跟圖示無關，已排除。
- `0x745670`（`CSpellListXML::parse`）反組譯出來的完整 XML schema（供之後有人要重查時參考，不用重新反組譯一次）：
  ```
  <spells>
    <spell id="..." desc="..." duration="..." delay="..." icon="..." range="..."
           align="Neutral|Chaotic|Lawful" required="0|1|2">
      <required mp="..." hp="...">
        <catalyst nameid="..." count="..."/>
      </required>
    </spell>
  </spells>
  ```
  對應的 56-byte config 物件欄位：`+0x00`=id、`+0x14`=icon、`+0x18`=range、`+0x1C`=align、`+0x20`=desc（內嵌 std::string）。**這個物件在正常遊玩流程中不會被建立**，只是留紀錄避免下次重查一次。

## 清理狀態（2026-09-15 這篇文件最後更新時）

這次新增又移除的暫時診斷／hook：

- `InventoryDebug_DumpSpellDbRecord()`：**已移除**，spell_db 記錄內容對不上已知 `castgfx`，沒有利用價值。
- `InventoryDebug_FindJustClickedSkill()` 裡原本多印的 80-bytes hex dump：**已移除**，確認全是 0 之後沒有繼續保留的理由。
- `SpellIconHook.cpp/.h`：**第一版**（hook `0x745220` setIcon 進入點）驗證完「setIcon 沒被呼叫」後已刪除；**因為使用者要求繼續追查，同一天又重建了第二版**，改成 hook `CSpellListXML::parse` 本體進入點（`0x745670`，`InstallSpellListParseHook()`），驗證完「parse() 本身也沒被呼叫」的結論後，**目前這個檔案跟呼叫點還留在專案裡、還部署在客戶端上**——下次接手時，如果 CE 數值掃描沒有指向另一個需要驗證「某函式有沒有被呼叫」的候選，這個探測 hook 應該要拿掉（正常遊玩不受影響，只是留著沒有用）。

保留的部分：`InventoryDebug_FindJustClickedSkill()` 本體（含 `[Pss][diag] found clicked skill ...` 診斷 log）——這是唯一驗證成功、之後要轉正式功能會用到的部分，先留著，log 之後轉正式時再依「Log 原則」收斂。

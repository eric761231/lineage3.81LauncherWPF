# 崩潰追查：堆積損毀（Heap Corruption）當機

> 寫作日期：2026-09-10
> 狀態：**已查出當機類型跟大致方向，尚未找到真正寫壞記憶體的根因**——heap corruption 類型的 bug，偵測到的地方（`free()`）跟真正寫壞記憶體的地方常常不是同一處，這份文件記錄目前查到的證據跟已排除的方向，之後再遇到同類當機可以接著查，不用重查一遍。

---

## 1. 事件

- 使用者回報「DDrawCompat 畫面沒反應」，懷疑卡頓，詢問是否要看 dmp。
- 確認 dump 檔位置：`D:\天堂資料\天堂專案#380客戶端+自製登入器\DDrawCompat-TW13081901.bin.dmp`（540MB，2026-09-10 18:47:37 寫入，Process Uptime 只有 5 分 10 秒——遊戲剛開沒多久就炸）。
- 同資料夾另外兩份 `DDrawCompat-TW13081901.bin[2].log`／`DDrawCompat-TW13081901.bin.log`：`[2].log` 那次（16:28~16:31）也有一次真正的當機紀錄（`16:31:55.178 Terminating application due to unhandled exception: 0xc0000005`），跟 dump 對應的那次（18:47）看起來是**不同次**的當機（時間對不上），但**類型可能一樣**，這次只深入分析了 dump 對應的那次。

## 2. 工具

這台機器有裝 Windows SDK 的 `cdb.exe`（x86 版，路徑
`C:\Program Files (x86)\Windows Kits\10\Debuggers\x86\cdb.exe`），可以直接分析 dump，不用另外裝東西。指令：

```powershell
$cdb = "C:\Program Files (x86)\Windows Kits\10\Debuggers\x86\cdb.exe"
$dmp = "D:\天堂資料\天堂專案#380客戶端+自製登入器\DDrawCompat-TW13081901.bin.dmp"
& $cdb -z $dmp -c ".ecxr; kb 30; lm; q"
```

`!analyze -v` 也能跑，但這次它的自動堆疊還原失敗（只給出一個 pseudo frame），改用 `.ecxr`（切到真正的例外 context）+`kb 30`（手動列 30 層堆疊）才拿到有用資訊。

## 3. 分析結果

**例外類型**：`0xc0000005`（存取違規），發生在 `ntdll!RtlpFreeHeap+0x418`，讀取位址 `0x00002800`（明顯不合法的小數值，典型堆積中繼資料被寫壞的樣子）。

Windows 自動分類（`!analyze -v` 的 `Failure.Bucket`）：
```
INVALID_POINTER_READ_ACTIONABLE_EntryCorruption_c0000005_ntdll.dll!RtlpAnalyzeHeapFailure
```
→ 這是**堆積損毀**的標準特徵，不是單純的 null pointer 或當機卡死。

**完整呼叫堆疊**（`.ecxr` 之後 `kb 30`）：
```
ntdll!RtlpFreeHeap+0x418
ntdll!RtlpFreeNTHeapInternal+0x6b5
ntdll!RtlFreeHeap+0xca
AcLayers!NS_FaultTolerantHeap::APIHook_RtlFreeHeap+0x3d1
msvcr90!free+0xcd
TW13081901+0xa6b62
TW13081901+0xa6ea4
TW13081901+0xddd82
TW13081901+0xe31a0
TW13081901+0xe4bc6
TW13081901+0x39aaa8
0x74e002a（未解析）
```

## 4. 關鍵線索與判斷

1. **整條呼叫鏈完全沒有 `LauncherDll.dll` 的任何一格**——全部是 `TW13081901`（遊戲本體）自己的程式碼呼叫 `free()`，中間經過系統的 `msvcr90`／`ntdll`。`LauncherDll` 有載入（`lm` 模組清單看得到 `68640000 686ae000 LauncherDll`），但沒出現在這次崩潰的堆疊裡。
2. **`AcLayers!NS_FaultTolerantHeap` 是關鍵線索**——這是 Windows 內建的「容錯堆積」相容性補丁層，**只有 Windows 自己的相容性資料庫偵測到某支執行檔有反覆堆積損毀當機的歷史，才會自動套用**。也就是說 `TW13081901.bin` 這支執行檔本身**在 Windows 的相容性資料庫裡已經被記錄有這個問題**（可能是原廠這支 2001 年老客戶端自己的既有 bug），連這層防護都擋不住才真的炸掉。
3. 綜合以上，**目前證據指向遊戲本體既有的堆積損毀舊 bug，不是這個專案新增的 hook/patch 造成的**。但 heap corruption 類型的 bug 有個天生限制：真正寫壞記憶體的地方，跟偵測到當機的地方（這次是某次 `free()`）常常不是同一處、甚至隔了一段時間——沒辦法從這一份堆疊 100% 排除「某次跟我們的 hook 互動間接誘發」的可能性，只能說**目前沒有直接證據**指向我們自己的程式碼。

## 5. 已排除 / 未排除

- 已排除：`VitalsPacketHook.cpp` 那次已知會斷線的 bug（見 `MimirPowerHook.cpp` 開頭註解跟 `LauncherDll.cpp` 的 `InstallVitalsPacketHook()` 呼叫已註解停用）——這次分析的兩次當機，時間點跟那個問題無關，而且那個 bug 的症狀是選完角色立刻斷線，不是堆積損毀。
- 未排除：是否任何一個自製 hook（`SmoothRunPatch`／`MimirPowerHook`／`AutoPotionOverlay` 等）曾經在**更早之前**寫壞過堆積、這次只是延遲發作——沒有證據支持，但也沒辦法用這一份 dump 完全排除。

## 6. 下次再遇到時建議

1. 留意當機發生前**最後做了什麼操作**（開哪個介面、連續動作、切換場景等），heap corruption 常常要配合「觸發時機」才好縮小範圍，光看 dump 堆疊通常查不到真正根因。
2. 如果能重現，開啟 Windows 內建的 **Application Verifier**（`appverif.exe`，針對 `TW13081901.bin` 開 Heap 檢查）跑一次，可以讓損毀在**真正寫壞的當下**就當機，而不是延遲到某次 `free()` 才爆——這樣抓到的 dump 才會指到真正的根因，而不是這次這種「下游」堆疊。
3. 同資料夾的 `[2].log`（16:28~16:31 那次）如果也有對應的 dump，可以比對兩次的堆疊是不是同一種模式，能增加「這是既有反覆發作的舊 bug」的信心。
